# Preview Deploy — Plan

Self-hosted preview deployments for PRs, served only on Filip's private Tailscale network.

## 1. Trigger path

- Each App repo adds a small workflow (`.github/workflows/preview-deploy.yml`) that calls a **reusable workflow published from this repo** (`filipkauffeldt/preview-deploy/.github/workflows/preview-deploy.yml@main`).
- Triggers: `pull_request` opened / synchronize / reopened → deploy; `closed` → teardown. Fork PRs are skipped (no secrets, and fork code must never run on the tailnet).
- The workflow runs the official **tailscale/github-action** (shared OAuth client, tagged, ACL'd to only reach the Server node) and POSTs a **Deploy Event** to `https://preview-server.{tailnet}.ts.net/deploy-events`: `{app, pr, sha, action: create|update|teardown}`.

## 2. Server

- **C# ASP.NET Core app, shipped as a Docker container** on the Server (`docker compose up -d`).
- Docker socket mounted → manages sibling containers; all Preview Deployments join a shared Docker network `preview-net`.
- **SQLite** for state: Apps, config, secrets (AES-encrypted, key file mounted from host), deployment records, queue.
- **Tailscale sidecar container** runs `tailscale cert` in renew mode for the wildcard cert `*.preview-server.{tailnet}.ts.net`; shared volume with the app.
- Clones App code via **HTTPS + fine-grained PAT** (shallow, single branch, exact SHA).

## 3. Deploy flow

1. Validate the **per-App token** (generated by the Server at App registration; pasted into the App repo's GitHub Secrets).
2. Enforce **per-App preview cap** (default 5). Updates to a PR that already has a Preview Deployment bypass the cap; new PRs over cap are **queued** (one coalesced entry per PR, latest SHA wins).
3. Build from the App's **Dockerfile**, or from the App's `preview-compose.yml` when present (Server injects an override joining the routed service to `preview-net`; no host ports published).
4. Container(s) labeled (`app`, `pr`, `sha`) for restart reconciliation. YARP routes `pr-{n}-{app}.preview-server.{tailnet}.ts.net` to the container by network name.
5. Health check on the configured path; failures reported.

## 4. Feedback

- **Sticky PR comment** (`peter-evans/create-or-update-comment`, `GITHUB_TOKEN` with `pull-requests: write`): "queued (#2 of 2)" → "deploying" → "ready at URL" → tombstone on teardown. Build failures reported in the comment and the UI.

## 5. Teardown

- PR close/merge → teardown event.
- Periodic **sweep**: reconcile closed PRs via GitHub API (catches missed events) + per-App **age TTL** (default 14 days, configurable), then `docker image prune`.

## 6. Management UI (Razor Pages)

Served on the tailnet, same C# app, no separate toolchain.

- Dashboard: Apps, deployments, queue, limit usage, status.
- Deployment detail: live logs, URL, rebuild/teardown.
- Queue: promote, cancel, deploy any open PR (via GitHub API), links back to PRs.
- App config: register App (owner/repo), build settings, env vars, secrets, limits, TTL.
- Account: change admin password.

## 7. Auth

- **Deploy Events**: per-App bearer tokens.
- **UI**: first run prints a one-time setup token to container logs → create admin username + password (Argon2-hashed); changeable in the UI. Tailnet membership is the outer boundary.

## 8. Limits

- Build concurrency cap (default 2), queued beyond it.
- Per-App preview max (default 5) with queue; rejection with a clear PR comment when the queue is disabled or overrun.
- Container memory caps (default 1 GB, per-App configurable).

## 9. App manifest

Optional `preview-deploy.yml` in the App repo **pre-fills** Server config at registration (Server config always wins):

```yaml
port: 3000
healthcheck_path: /
compose: preview-compose.yml
service: web
memory: 1gb
ttl_days: 14
```

## 10. Extensibility

- **Custom domains later**: LE DNS-01 wildcard cert for a real domain that only resolves privately (internal DNS wildcard or MagicDNS split-DNS). YARP matches by Host header; the cert source is the only pluggable bit. No rework required.

## Open design notes

- Compose `ports:` sections in App files are ignored/stripped — routing is purely internal via `preview-net`.
- Rejected-at-cap deployments surface in the PR comment and can be re-triggered by re-push or from the UI.
